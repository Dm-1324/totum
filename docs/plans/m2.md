# Milestone 2: Permission spine

## Done when
A tier-2 call blocks until approved; every call appears in the log

## How we'll prove it
1. `packages/main/src/permission-flow.test.ts`: real host handler + engine + `:memory:`
   SQLite, fake agent and fake UI behind main's real router. A `test.danger` call stays
   pending (no run, no result) until the UI answers; approve -> it runs; reject -> it
   doesn't, and the agent gets `rejected`. After a scripted mix of calls (ok, not
   granted, rejected, invalid input, approval timeout), `audit.list` has one row per call.
2. `pnpm dev`: type `/call test.danger {}`. A dialog appears and the chat waits; Approve
   -> the reply comes back. The Log panel shows every call, with Undo on the `test.note` row.
3. `host-db.process.test.ts`: the built host, forked as a real Electron utility process,
   opens its DB file via `node:sqlite` and writes an audit row (catches an Electron build
   without sqlite).

## Boundary check
- `node:sqlite`, `node:path`: host only (utility process; host is the OS owner). DB path
  comes from main (`app.getPath`), since a utility process has no `app`.
- `capability.ts` + specs in shared: types and zod only, no runtime OS access;
  `shared-allowed-imports` unchanged. `run`/`undo` are implemented and called only in host.
- Agent: no new imports. It sends `capability.request` over its existing MessagePort;
  it never sees `permission.ask` and can't answer one (that route is host<->main<->ui only).
- main relays and validates every message with zod and adds the origin; it never runs a
  capability or decides a permission. The host engine is the only gate.
- ui: new named preload functions only, no generic send; answers checked against the
  trusted window and an open ask id. All dialog/log text rendered as text nodes.

## Decisions needed
Settled with the user 2026-10-03:
1. **SQLite: `node:sqlite`** (built into Electron 44 / Node 24.21; no native module,
   no electron-rebuild). ADR 0005 in slice 1.
2. **Agent->host: relay through main.** Fits the existing supervisors, main validates
   both ways, restarts need no port rewiring.
3. **Missing grant: ask the user** (session / always / deny); deny -> `not_granted`.
4. **Trigger before M3: `/call` chat command through the agent**, dev/test builds only,
   same `CapabilityRequest` schema as M3.
5. **Grant prompt rules** (user, 2026-10-03): exact scope shown; `always` only for tier
   0/1 and never when suggested by untrusted content; denied grants remembered per task;
   max 3 grant prompts per task. Recorded in ADR 0005.

## Out of scope
- `task` grant lifetime and real task boundaries (M3; M2 treats one chat message as one task).
- Editing an action in the approval dialog (M5, with `shell.execute`).
- Real capabilities (`files.*`, `clipboard.*`, `context.active`: M4).
- Model, plans, budgets, stop (M3). Styled command bar (M6). Audit export/retention.


## Additional rules (from review)

Grant prompts:
- The prompt names the exact scope (folder, app or account), not just the
  capability.
- "Always" is offered only for tier 0 and 1. Tier 2/3 grants are this session
  at most, and those calls still ask for approval every time.
- If the step was suggested by untrusted content, the prompt says so and
  offers no "always".
- A denied grant is remembered for the rest of the task, so no asking again
  in a loop. At most 3 grant prompts per task; then stop and tell the user.

Triggers:
- The /call parser and test.* capabilities exist only in dev and test builds;
  add a test that a production build registers neither.
- /call input goes through the same capability.request schema the model will
  use in M3; no shortcut path.
